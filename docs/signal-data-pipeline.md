# 보행신호 데이터 파이프라인 — 프로덕션 설계

> **문제:** 전국 모든 횡단보도의 `cycle/green`(신호 주기·녹색시간)을 어떻게 확보·갱신하나.
> **관련:** [`transit-routing-gtfs.md`](transit-routing-gtfs.md) §3.4(신호 소스) · §7(도보·신호 모델)
> **핵심 결론:** 신호는 **요청마다 실시간으로 가져오는 게 아니라, 오프라인 정적 테이블로
> 미리 구워 두는** 문제다. 전국 정확 타이밍은 기술이 아니라 **경찰청 데이터 협약(B2G)** 문제다.

---

## 1. 왜 실시간이 아니라 정적인가

설계 §7.1이 정한 것: **실시간 신호 위상은 유효기간이 초 단위다.** 지금 초록인 걸 알아도
30분 뒤 환승 지점의 위상은 감응식·TOD로 바뀌어 외삽이 무너진다. 그래서:

| 구간 | 쓰는 값 | 필요 데이터 |
|---|---|---|
| **첫 횡단보도만** | 실시간 위상 투영 | 실시간 API(있는 도시만) |
| **나머지 전 구간** | 기대대기 `(cycle − 유효녹색)²/(2·cycle)`, 유효녹색=green−횡단시간(§7.4) | **정적 cycle/green** (그래프에 미리 구움) |

→ 프로덕션의 데이터 문제 = **전국 cycle/green 정적 테이블을 배치로 조립·갱신**하는 것.
요청 경로에선 신호 API 0콜(§7.3). 이게 확장 가능한 이유다.

---

## 2. 소스 계층 — provenance + 우아한 저하

각 횡단보도 타이밍은 **어느 계층에서 왔는지(source)+신뢰도**를 들고 다니고, 계산은 최상위
소스를 쓰되 UI가 "정확/추정"을 구분한다.

| 계층 | 소스 | 커버 | 비고 |
|---|---|---|---|
| **1. 표준데이터** | 전국횡단보도표준데이터(15028201) + 신호등표준데이터(15028198) | ⚠️ **지자체 자율** | §3 참조 — 스키마엔 녹색/적색시간이 있으나 참여·채움이 불균등 |
| **2. 경찰청 TOD** | 경찰청/도로교통공단(UTIC, 15159340) 신호운영계획 | 현재 인천·대구, 확장 중 | **권위 소스** — 시간대별 cycle/green. 실서비스는 여기 **B2G 협약이 답** |
| **3. 실시간** | 교통안전 실시간(15157604) | 서울·제주·울산만 | **첫 횡단보도 위상 보정만** (백그라운드 폴링→메모리) |
| **4. 관측 추론** | 자체/크라우드 폴링 → `infer_timing` | 실시간 API 있는 곳 | 버스 수집과 같은 발상. 단 1~2초 해상도 필요라 얇다 |
| **5. Fallback** | 도로등급별 국가평균 cycle/green(간선~150s·이면~90s) or 거리별 RoadUpper | 전부 | **절대 실패 안 함** — "추정" 표시로 저하 |

## 3. ✅ 실측 — 15028201(표준데이터)로 판교가 되나 → 안 된다

data.go.kr 원문 확인(2026-07):

- **스키마엔 타이밍이 있다** — 컬럼에 `녹색신호시간`·`적색신호시간` 존재. cycle = 둘의 합으로
  계산 가능. (예상과 달리 '신호등 유무'만 있는 게 아니다.)
- **그러나 지자체 자율 업로드다** — 현재 **55개 기관만** 참여, 갱신 **반기**, 소관 국토부·경찰청,
  제공 지자체. 매월 초 병합해 전국 단위 제공.
- **성남시는 미참여** — "성남시 횡단보도" 표준데이터셋 검색 **0건**. → **판교가 15028201에 없다.**
- **참여 지역도 타이밍은 안 채운다** — 샘플(무주군) 전체 행에서 `녹색/적색시간` **100% 공란**,
  신호등이 있는 행(`보행자신호등유무=Y`)조차 비어 있다. 참여 55개 기관도 **소도시·군 위주**
  (거제·무주·이천·구리·양산…)로 서울·성남·수원 같은 대도시는 빠져 있다.

**→ 15028201은 실질적으로 '타이밍 소스'가 아니라 '횡단보도 위치·신호등 유무·폭·연장' 소스다.**
cycle/green 을 지자체가 조사하지 않기 때문(그건 경찰청 소관) — 컬럼은 있어도 아무도 안 채운다.
판교는 아예 없고, 있어도 타이밍은 못 얻는다.

### 3.1 그래도 15028201에서 건지는 것 — 채워진 필드로 green 을 '유도'한다

타이밍은 비어도 **위경도·차로수·횡단보도폭·`횡단보도연장`·`보행자신호등유무`는 대체로 채워져
있다.** 이걸로 신호가 없을 때의 **원칙 있는 추정**을 만든다(순수 추측이 아니라 물리 기반):

| 아는 값(채워짐) | 유도 | 근거 |
|---|---|---|
| `보행자신호등유무` | 무신호면 **대기 0**, 신호면 아래 | 신호 없는 횡단은 대기 없음 |
| **`횡단보도연장`**(횡단거리) | **green ≈ 연장 ÷ 1.0 m/s + 여유** | 경찰청 매뉴얼: 녹색시간을 설계속도 1.0 m/s 로 산정 |
| `차로수`·도로등급 | **cycle ≈ 도로등급별 국가평균**(간선~150s·이면~90s) | 신호운영 지침 통상값 |

→ `expected_wait = (cycle − 유효녹색)²/(2·cycle)`(유효녹색=green−횡단거리/개인속도, §7.4)를
**유도된 cycle/green** 으로 계산하고 `source=derived`, `confidence=low` 로 표시한다. 순수
거리밴드(RoadUpper)보다 원칙적이다. 유효녹색으로 개인 도보속도까지 반영된다.

> 확인 도구: [`spike/validation/check_crosswalk_std.py`](../spike/validation/check_crosswalk_std.py) —
> 참여 지자체 CSV 를 받아 타이밍 채움률·해당 지역 커버를 판정한다.

## 4. 프로덕션 설계 원칙

1. **오프라인 우선.** 그래프 빌드 시 최선의 소스로 cycle/green 상수를 구운다. 요청 경로엔 신호
   API 0콜. 데이터 문제 = 주기적 배치이지 실시간 의존이 아니다.
2. **provenance + 신뢰도.** 각 횡단보도가 소스 계층과 confidence 를 들고 다닌다. UI 는 "정확
   (실측/경찰청)"과 "추정(fallback)"을 구분한다.
3. **시간대별(TOD).** cycle/green 은 첨두/평시가 다르다. 수집기 timeband처럼 밴드별 저장.
   경찰청 TOD 가 이걸 직접 준다.
4. **우아한 저하, 절대 블록 금지.** 없으면 fallback + "추정" 플래그. 공휴일·쿼터 처리와 같은 철학.
5. **가치순 우선 확보.** §6.3 — 신호 차별점은 `버스/도보 → 환승도보(신호) → 지하철` 절벽에서만
   성립한다. → **지하철역·환승 지점 주변 횡단보도부터** 정확 데이터 확보, 나머진 fallback.
   전국을 첫날 다 채울 필요 없다.
6. **갱신 루프 + 버전 추적.** 재타이밍되면 바뀐다. 표준데이터 반기 갱신·TOD 재수집 + 계획번호/
   적용기간 대조(신분당선 PDF 패턴, §3.3.1).

## 5. 로드맵 — 데이터 조달은 순서가 있다

| 단계 | 소스 | 목적 |
|---|---|---|
| **PoC/검증** | 현장 실측 3~5개(`infer_timing`) + fallback | 차별점이 성립하는지(§9)만 본다. 전국 불필요 |
| **초기 서비스** | 표준데이터(참여 지역) + 도로등급별 fallback | "추정" 표시로 전국 커버, 정확도는 참여 지역만 |
| **확장** | **경찰청/도로교통공단 TOD 데이터 협약** | 전국 시간대별 정확 cycle/green. B2G 계약 |
| **보정** | 실시간(서울·제주·울산) 첫 횡단 위상 + 관측 추론 | 실측 갱신·엣지 케이스 |

**핵심:** 처음부터 전국 실측/협약을 선불하는 건 순서가 거꾸로다. **표준데이터+fallback으로
시작 → 환승·역 주변 정확도를 측정 → 차별점이 §9에서 증명되면 그때 경찰청 협약에 투자.**

> **경쟁 관점(§9):** 카카오·네이버가 신호를 아예 모델링하지 않는 이유가 이 데이터 조달 마찰이다.
> 전국 정확 신호는 기술이 아니라 **경찰청과의 데이터 관계**가 해자다 — 그래서 차별점이 실측으로
> 증명된 뒤에만 그 비용을 지불할 가치가 있다.

## 6. 커버 안 되는 지역/횡단보도 처리 — 결정 사다리

한 횡단보도를 만났을 때 위에서 아래로 **처음 되는 것**을 쓰고, 그 `source`·`confidence`를 남긴다.
핵심은 **절대 막지 않고, 아는 만큼만 정직하게** 쓰는 것이다.

1. **경찰청 TOD 있음** → 시간대별 cycle/green (source=`tod`, 정확) ★
2. **표준데이터에 타이밍 채워짐** → 그 값 (source=`std`, 정확) — 현재는 거의 없음
3. **실시간 API 커버 + 첫 횡단** → 위상 투영으로 그 순간 보정 (source=`live`)
4. **관측 이력 있음**(자체/크라우드) → `infer_timing` 추정 (source=`observed`, mid)
5. **표준데이터에 연장·신호등유무만** → §3.1 유도(green=연장/1.0, cycle=도로등급) (source=`derived`, low)
6. **아무것도 없음** → 도로등급 국가평균 or 거리밴드 fallback (source=`fallback`, low)
7. **신호등 없음/모름** → 대기 0 (무신호 횡단)

**그리고 커버가 갈리는 걸 제품 UX로 흡수한다:**

- **정확도 뱃지**: 정확(`tod`/`std`) vs 추정(`derived`/`fallback`)을 경로에 표시. "이 구간 신호는 추정"
  이라고 밝히면, 틀려도 신뢰를 안 깬다(수집기 '추정' 표시·공휴일 처리와 같은 철학).
- **불확실성은 마진으로**: 추정 구간은 §6.6 안전 마진을 넓혀 "빠듯함"으로 표시 — 놓치게 만들지 않는다.
- **가치 있는 곳만 정밀화**: 차별점은 `버스/도보 → 환승도보 → 지하철` 절벽에서만 성립하므로(§6.3),
  **역·환승 지점 주변 횡단보도만** 실측/경찰청으로 승격하고 나머지는 추정으로 둔다. 판교가 커버
  안 돼도, **판교 환승 경로의 그 몇 개 횡단보도만** 실측하면 그 지역 차별점은 성립한다.

**즉 "커버 안 되는 지역"의 답은 전국을 채우는 게 아니라, (a) 유도값으로 전국을 안전하게 덮고
(b) 차별점이 걸린 소수 지점만 정밀화하고 (c) 정확/추정을 UI로 정직하게 구분**하는 것이다.
전국 정밀은 경찰청 협약이 오기 전까지는 목표가 아니다.
