# 기존 기술 Validator 결과

평가 프로토콜:
[`MEASUREMENT.md`](../MEASUREMENT.md)

이 문서는 동일한 Case 자료를 기존 기술 평가기에도 입력한 결과를 기록한다.
경량 검증과 판정 기준·입력 출처를 섞지 않는다.

## 비교 모델

- `Naver`
- `Speed`
- `Speed+Signal`
- `TMAP-Personal`
- `TMAP+Signal`
- `Kakao-Personal`
- `Kakao+Signal`

> **`개선천장`** (표에 남은 `TMAP개선천장`·`Kakao개선천장` 포함)은 **모델이 아니라
> 진단값**이다: 관측된 실제 신호대기(`actual.signal_wait_s`)를 도보 예측에 그대로
> 더한, "신호를 완벽히 알았을 때"의 도착오차 하한(천장). 실측 신호가 있어야 하므로
> 배포엔 못 쓰고 통과 게이트에도 안 들어간다. 예전 이름은 `Oracle`/`+RealSignal`
> 이었으나 '실측'이 실시간 신호 API로 오해돼 `개선천장`으로 바꿨다. 이 표들은 그
> 진단을 포함한 과거 실행 기록이다.

### 현재 `TMAP+Signal` 이름의 범위

현재 코드의 `TMAP+Signal`은 전체 대중교통 길찾기 모델이 아니다. 정확한
계산 범위는 **연결 이벤트 하나의 `TMAP 보행자 경로시간 + 신호대기
fallback`**이다. `score.py`는 이 값을 도보 시작시각에 더해 다음 정류장
도착시각만 평가한다.

아직 다음 과정은 구현·평가하지 않았다.

- TMAP 대중교통 경로를 기준으로 전체 버스 구간을 선택하고 재조립
- 모든 도보 환승구간의 시작·종료 좌표 자동 추출
- 버스 실시간 도착·출발 및 실제 주행시간 예측
- 동일 신호 제어기에 속한 연속 횡단 세그먼트 병합
- 각 횡단보도의 실제 주기·위상에 따른 신호대기 예측

따라서 아래 `TMAP+Signal` 결과는 완성된 전체 경로 모델의 정확도가 아니라,
현재 도보·신호 하위 모델의 정확도다. 오해를 막기 위해 해석상
`TMAP-Walk+SignalFallback`으로 읽는다.

새로 추가한 `journey_score.py`는 별도 모델
`TMAP-Journey+PersonalWalk+Signal`로, TMAP 대중교통 itinerary의 모든
WALK leg를 보행자 API로 재조회하고 대중교통 leg와 다시 연결한다.

API·좌표·주기·실시간 신호가 없어서 실행하지 못한 모델은 실패값이나 0초가
아니라 `unavailable`로 기록한다.

## 실행 원칙

- 공통 키는 `find-path/.env`, Validator 전용 키는 `spike/validation/.env`에서
  읽는다. `collector/.env`는 읽지 않는다.
- 채팅 관측을 먼저 `ground_truth.json` 형식으로 정규화한다.
- `source: real`, `split: test`로 기록한다.
- 캡처에서 확인할 수 없는 값을 추정해서 정답으로 넣지 않는다.
- 실제 신호 대기는 `개선천장`에만 사용한다.
- TMAP·카카오·실시간 신호의 성공 여부와 커버리지를 Case마다 기록한다.
- API 결과를 보고 개인 시간비율이나 안전마진을 변경하지 않는다.
- 기술 모델의 종합 판정은 유효한 `test` 연결 이벤트 3건 이상에서만 한다.

### 전체 여정 연결 모델 실행

2026-07-24 15:22, 동일 출발지·목적지로 TMAP 대중교통 후보 10개를 실제
조회했다. 관측·네이버 경로 `6211 → 9401 → 3`은 후보에 없었다. 따라서
이 관측의 실제 `75:05.34`와 TMAP의 다른 물리 경로를 같은 모델 오차로
계산하지 않는다.

진단을 위해 TMAP 후보 0
`241 → 9409 → 231`의 모든 WALK leg를 보행자 API로 재조회해 연결한
결과는 다음과 같다.

| 구성요소 | 시간 |
|---|---:|
| TMAP 대중교통 이동 sectionTime | 4096.00초 |
| 개인화 순수 도보 | 358.43초 |
| 검출된 보행신호 대기 | 0초 |
| 승차 대기 | 미입력 |
| 승차 대기를 제외한 하한 | 4454.43초 |

예상 도착은 `16:36:14.43`이지만 대중교통 leg 1·3·5의 승차 대기가
없으므로 `complete=false`다. 이 값은 완성 예측이나 실제 대비 정확도가
아니다. 다만 **대중교통 뼈대 → 전 도보 재조회 → 개인속도 → 신호 →
대중교통 이동**의 연결 파이프라인 자체는 실제 API로 끝까지 실행됐다.

### ⚠️ 갱신 — 세그먼트 병합 적용 (2단계 횡단 → 1 신호)

TMAP이 2단계 횡단(중앙분리대)을 세그먼트 여러 개로 쪼개 신호를 과다 계상하던 것을,
인접 세그먼트를 하나의 신호로 병합하도록 고쳤다(`tmap_client.merge_adjacent_crosswalks`).
**Case 1: 6 세그먼트 → 3 신호, RoadUpper 신당 210→150·판교 420→300·합계 630→450초.**
아래 상세 표는 모두 **병합 후** 값이다.

| 도착 MAE | 병합 전 | 병합 후 |
|---|---:|---:|
| Speed+Signal (수동 E1+E3) | 207.92초 | **117.9초** |
| TMAP+Signal (수동 E1+E3) | 226.40초 | **136.4초** |
| Speed+Signal (score.py CAL+E3) | 258.6초 | **168.6초** |
| TMAP+Signal (score.py CAL+E3) | 275.2초 | **185.2초** |

연결 안내(100%)·판정은 불변 — 배차버스라 신호가 연결 게이트에서 제외되므로 이
개선은 **도착 MAE(진단값)만** 낮춘다. 단 RoadUpper는 여전히 상한이라 실제
212.55초보다 보수적(450초)이다 — 크기까지 맞추려면 횡단보도 cycle/green 실측이
필요하다(§7.4).

### E1+E3 도보 도착오차 진단

한 번의 전체 이동에서 나온 두 이벤트를 독립된 두 Case로 세지는 않지만,
관측된 신호 3개를 모두 반영한 진단 MAE는 다음과 같다.

| 모델 | 예측의 신호 처리 | 진단 n | MAE |
|---|---:|---:|---:|
| Naver | 네이버 원본시간 | 2 | 46.52초 |
| Speed | 신호 미포함 | 2 | 107.09초 |
| Speed+Signal | RoadUpper(병합): E1 150초·E3 300초 | 2 | 117.9초 |
| 개선천장 | 실제 3개·212.55초 | 2 | 5.62초 |
| TMAP-Personal | 신호 미포함 | 2 | 88.60초 |
| TMAP+Signal | RoadUpper(병합): E1 150초·E3 300초 | 2 | 136.4초 |
| TMAP개선천장 | 실제 3개·212.55초 | 2 | 17.67초 |

여기서 실제 신호 3개·`212.55초`는 `개선천장` 계열에만 들어간다. 제품 예측인
`Speed+Signal`과 `TMAP+Signal`은 결과를 보기 전에 정해야 하므로 실제값을
사용할 수 없고, 병합 후 fallback 예측 `450초`(E1 150초 + E3 300초)를 쓴다.
신호만 비교하면 실제보다 `237.45초` 과대예측한다(병합 전 630초·+417.45초).

| E1+E3 합산 | 순수 걷기 | 신호 | 총 도보 | 실제 총 도보 대비 |
|---|---:|---:|---:|---:|
| 실제 | 654.42초 | 212.55초 | 866.97초 | 0초 |
| Speed+Signal | 652.80초 | 450.00초 | 1102.80초 | +235.83초 |
| 개선천장 | 652.80초 | 212.55초 | 865.35초 | -1.62초 |

따라서 실제 약 3분 30초를 기다렸는데도 개선천장에 작은 오차가 남는 이유는
신호가 아니라 순수 걷기 예측 때문이다. E1은 `-6.43초`, E3은 `+4.81초`
방향으로 빗나가 합산하면 `-1.62초`다. 앞 표의 개선천장 `5.62초 MAE`는 두
이벤트의 절대오차 평균이므로 방향이 다른 오차를 상쇄하지 않는다.

`TMAP+Signal`의 E1+E3 합산 오차 `+272.79초`는 다음처럼 분해된다(병합 후).

| 오차 원인 | 예측 | 실제 | 과대예측 |
|---|---:|---:|---:|
| TMAP 개인화 순수 걷기 | 689.76초 | 654.42초 | +35.34초 |
| 신호 fallback(병합) | 450.00초 | 212.55초 | +237.45초 |
| 합계 | 1139.76초 | 866.97초 | **+272.79초** |

전체 과대예측의 약 `87%`는 아직 신호 fallback에서 발생한다. **세그먼트 병합으로
개수 문제(6→3)는 해결됐지만**(630→450초), 남은 과대예측은 RoadUpper 밴드 상한이
실제 대기보다 보수적이기 때문이다 — 이건 횡단보도 cycle/green 실측으로만 좁혀진다.

### 기술적 관찰

- E1에서 Speed의 순수 걷기 오차는 `6.43초`뿐이지만 실제 신호
  `118.93초`를 생략해 총 도착 오차가 `125.36초`가 됐다. E3에서도 순수
  걷기 오차는 `4.81초`뿐이지만 신호 2개·`93.62초`를 생략해 오차가
  `88.81초`가 됐다.
- 실제 신호 3개를 이벤트별로 더한 개선천장의 E1+E3 MAE는 `5.62초`다.
  세그먼트 병합 후 RoadUpper Speed+Signal MAE는 `117.9초`로 내려왔지만(병합 전
  207.92초) 여전히 보수적이다. 다음 기술 가설은 속도비율보다 신호 대기 추정
  정확도(밴드 상한 → 실측 cycle/green)에 집중해야 한다.
- 142와 6211은 실제로 다음 환승 지점에 동시에 도착했으므로 그룹 단위로
  둘 다 적중 처리했다. 차량 단위 정확도는 분 단위 ETA와 차량 고유 ID가
  없어 판정하지 않았다.
- E2는 경로 대체로 하차 위치가 달라졌을 가능성이 있어 대표 점수에서
  제외했다. E3의 신호 2개는 위 보조 결과와 진단 MAE에 포함했다.
- `score.py`의 엄격한 연결 평가는 초 단위 후보 출발시각과 차량 식별자가
  없어 실행하지 않았다. 위 표는 캡처·관측값으로 계산한 수동 독립
  평가이며, API 모델의 값은 만들어 넣지 않았다.
- 위 오차는 **첫 정류장 도착 예측** 지표다. 전체 여정은 네이버 예정
  `16:44`보다 실제 `16:37:05.34`에 끝나 약 `6분 54.66초` 빨랐다.
  하위 예측 오차와 최종 사용자 효용은 별도 지표로 유지한다.
- 최종 단축분에는 네이버의 출발 대기 6분과 버스 지연·대체 탑승이
  포함되므로, 기술 모델이 같은 연결을 사전에 선택했는지 확인하기 전에는
  모델 순증분으로 귀속하지 않는다.
- Validator 전용 `.env`의 TMAP·Kakao·신호 키는 모두 정상 로딩됐고 실제
  호출에 성공했다. 키 미설정으로 기록했던 이전 상태는 해소됐다.
- Kakao 장소 검색은 출발지 아파트를 찾았지만 버스정류장 `02187`을 직접
  반환하지 않았다. 신당누리센터 건물을 종점으로 쓰면 Kakao `1,039m`,
  TMAP `939m`로 네이버 781m와 다른 경로가 되어 공식 평가에서 제외했다.
- TMAP 경로상 네이버 781m와 일치하는 두 번째 횡단보도 끝점을 정류장
  추정 위치로 두면 TMAP은 `791m·476.51초`, Kakao는 `882m·531.33초`였다.
  실제 순수 걷기 455.23초에 대한 오차는 각각 `21.28초`, `76.10초`다.
  종점이 추정값이므로 위 모델별 표는 진단용이며 종합 `유효 n`에는 넣지
  않았다.
- TMAP은 이 조건부 경로의 **서울 구간**에서 횡단보도 2개를 검출했다.
  서울에 있으므로 실시간 API 조회 대상에는 포함했으며 API도 교차로 지도
  4,239건과 실시간 신호 1,399건을 정상 반환했다. 다만 두 횡단보도의
  최근접 실시간 지원 교차로가 각각 약 `446.6m`, `419.0m` 떨어져 50m
  매칭 기준을 통과하지 못했다. 즉 지역 때문에 호출을 생략한 것이 아니라
  해당 횡단보도가 반환된 지원 교차로 목록과 매칭되지 않은 것이다.
  따라서 설계 문서 §7.4에 따라 횡단보도마다 거리별 RoadUpper fallback을
  `Speed+Signal`, `TMAP+Signal`, `Kakao+Signal`의 공식 평가값에 반영했다.

### score.py 재평가 — 실측 좌표·cliff 규칙

인코딩한 두 이벤트: **`2026-07-23-CAL-6211`**(calibration, 모델 학습용 → **판정
제외**)과 **`2026-07-24-E3-55`**(test). ⚠️ **CAL은 7/23의 별개 트립**이라, 앞의
'핵심 E1'(7/24 Case 1 첫 도보, 신호 118.93초)과는 다른 날·다른 이벤트다.

`score.py --tmap --signals` 실행. 처음엔 TMAP+Signal이 CAL에서 오답이었는데,
원인은 신호가 아니라 **TMAP이 종점을 건물 좌표(939m)로 잡아** 도보를 부풀린
것이었다. 종점을 **실측 정류장 좌표**로 해석하도록 고치니(`stop_client` —
ARS→TAGO `getSttnNoList` 역조회) 정리된다. 두 이벤트 모두 배차버스(`cliff: false`)라
신호는 연결 게이트에서 제외한다(§6.3).

신호는 **상한(RoadUpper)과 유도(derived) 두 추정기를 다 계산**해 소스별 모델로 넣는다
(`score.py` 가 `…(상한)`·`…(유도)` 자동 출력). 유도는 횡단거리로 green 을 유도한 '평균'
추정으로, 공공데이터에 주기가 없을 때의 배포 가능한 값이다(§7.4·signal-data-pipeline).

> ⚠️ **아래 표는 진단용(CAL+test 합산 n=2)** — CAL(7/23)은 모델 학습표본이라 **통과 판정에서 제외**된다(프로토콜). **판정 대상은 test-only n=1**(7/24 E3)이고 결론은 '판정 보류'다(아래 최종 판정). '0%→100%'는 진단 헤드라인이지 통과 근거가 아니다.

| 모델 | CAL(7/23·진단) | test(7/24 E3·판정) | 연결정확도(진단 n=2) | 도착 MAE(진단) |
|---|---|---|---:|---:|
| **Naver (기존 지도)** | 6211_next 오답 | 3 오답 | **0%** | 97.2초 |
| **TMAP-Personal** (도보) | 6211_early 적중 | 55 적중 | **100%** | 39.8초 |
| **TMAP+Signal(상한)** (RoadUpper·병합) | 적중 | 적중 | **100%** | 185.2초 |
| **TMAP+Signal(유도)** (횡단거리 유도·병합) | 적중 | 적중 | **100%** | **21.4초** |
| (참고) 개선천장 (실측 신호) | 적중 | 적중 | **100%** | 8.8초 |

Speed 계열도 동일: Speed+Signal(상한) **168.6초** vs Speed+Signal(유도) **14.0초**.

- **좌표 보정으로 결과가 뒤집힌다.** md 방식(도보 재정의)이 연결·도착 두 축 모두에서
  네이버를 이긴다: 연결 0%→**100%**, 도착 MAE 97.2→**39.8초**.
- **유도 추정이 상한을 압도한다** — TMAP+Signal 상한 185.2초 → 유도 **21.4초**(실측 8.8초에
  근접). 상한은 항상 과대(절벽 안전용), 유도는 평균(도착시각 정확). 둘 다 배차버스라 **연결엔
  영향 없다**. 유도 추정으로 **공공데이터에 주기가 없어도** 배포 가능한 정확도가 나온다.
- ⚠️ 유도는 평균이라 과소예측 위험 — 절벽 trip 에선 안전마진/상한을 쓴다(§7.4).

## ★ 절벽 시나리오 — 신호 차별점 메커니즘 실증 (demo)

Case 1 이 배차버스라 못 잰 **신호가 연결을 뒤집는 차별점**(§6.3의 유일 성립 조합
`도보(신호)→지하철`)을 설계 시나리오(`2026-07-25-CLIFF-demo`)로 실증했다.
⚠️ **`source=demo`(발명한 예시)라 통과 판정에서 제외**된다 — 이건 **메커니즘·validator
준비도 실증**이지 실측 검증이 아니다. **실제 절벽 trip 관측이 최종 단계.**

설정: 환승 도보에 큰 신호(실제 130초). 지하철 T1 08:04:10 · T2 08:07:10(헤드웨이 3분).
`cliff=true`(지하철 시각표라 놓치면 다음 열차).

| 모델 | 선택 연결 | 판정 | 위험오답 |
|---|---|---|---|
| Naver (지도·무신호) | T1 | ❌ 오답 | ⚠️ **위험** |
| Speed (빠른속도·무신호) | T1 | ❌ 오답 | ⚠️ **위험** |
| **Speed+Signal(유도 71s)** | **T2** | ✅ **적중** | - |
| **Speed+Signal(상한 150s)** | **T2** | ✅ **적중** | - |

- **핵심**: 절벽에선 **지도도, 빠른 속도만으로도 "T1 탄다"고 위험하게 안내**하지만, 실제론
  신호 때문에 T1 을 놓치고 T2 를 탄다. **오직 신호 반영 모델만 T2 를 맞힌다.** §1 가설이 노린
  바로 그 차별점이다.
- **속도만으론 위험하다** — 빠른 속도가 신호를 상쇄 못 하는 빠듯한 절벽에선 Speed(무신호)가
  지도와 똑같이 위험오답을 낸다. **신호가 필수다.**
- **유도(71s)가 실제(130s)를 과소예측해도 연결은 맞혔다** — miss 임계만 넘으면 되기 때문.
  단 더 빠듯하면(임계가 71~130 사이) 유도는 "탄다"(위험)·상한(150)은 "놓친다"(안전)로 갈린다 →
  **절벽에선 상한 또는 유도+안전마진**을 쓰는 이유(§7.4·§6.6).

`유효 n`은 도보 도착오차를 계산할 수 있는 이벤트 수다. E1과 E3을 포함해

### 최종 결론

- **연결 안내: 기존 지도 0% → 제품 100%** (실측 좌표 기준, n=2, 위험오답 0). 도보
  속도 반영이 지도의 '다른 버스' 오답을 실제대로 교정한다. **속도 개인화는 실측 검증됨.**
- **병목은 도보가 아니라 신호 예측** — 순수 걷기 오차는 4~6초로 작다(개선천장 MAE
  5.62초). **세그먼트 병합(6→3)+유도 추정으로 Speed+Signal MAE 258→14초**까지 내려와
  공공데이터 주기 없이도 배포 가능(§7.4). 상한(RoadUpper)은 절벽 안전용으로 병행.
- **신호 차별점 — 메커니즘 실증됨, 실측 관측 남음.** Case 1(배차버스)은 신호가 연결을
  안 바꿔 못 쟀지만, 절벽 시나리오(demo)에서 **지도·속도만은 위험하게 T1 안내·신호 모델만
  T2 적중**을 실증했다(§절벽 시나리오). 단 `source=demo`라 통과엔 안 들어간다.
- **판정 보류** — 두 축 다 방향은 확인. 남은 것: (1) 실 test 3건(속도 축, 현재 1건),
  (2) **실제 절벽 trip 1건 관측**(신호 축). 판교 신호 3개는 유도로 덮이므로 실측 없이 시작 가능.
