# 개인화 연결 예측 검증

목표는 간단하다.

> 같은 실제 이동에서 `네이버 원본 → 개인 속도 → 개인 속도+신호` 순으로
> 정류장 도착시각과 연결편 판정이 실제에 가까워지는가?

전체 앱·GTFS·그래프 빌드는 필요 없다. 사용자가 올린 지도 캡처와 스톱워치
타임라인을 연결 이벤트 단위 JSON으로 옮겨 `score.py`로 평가한다.

---

## 1. 가설과 통과 기준

★ **판정 대상은 '어느 모델을 써야 하나'가 아니라, 이런 식으로 도보 속도 + 보행신호
대기를 반영한 접근이 기존 지도보다 나은가(적합성)**이다. 상한·유도 같은 여러 추정
방법이 있고, 그 방법들로도 지도보다 개선되는지를 본다.

검증 대상은 **도보 속도와 보행신호 대기를 반영하면 기존 지도(네이버·카카오)보다
더 정확한 연결 안내를 준다**는 것이다. 여기서 '정확'은 도착시각 정밀도가 아니라
**안내한 연결이 실제와 맞는가**로 정의한다 — 지도가 명시한 것과 **다른 버스를
타거나**, 지도보다 **더 대기하거나**, 그 버스를 **놓치는** 경우를 지도의 부정확으로
보고, 그때 우리 모델이 실제를 맞히는지를 잰다.

**제품은 단일 모델이 아니라 맥락별 추정기**다 — 절벽(지하철)엔 **상한**(과소예측→놓침을
막는 안전값), 배차버스엔 **유도**(도착시각 정확). 접근이 각 맥락에서 옳게 배포됐을 때
지도를 이기는지를 본다.

고정한 접근을 **새로운 연결 이벤트 3건 이상**에 적용했을 때:

1. 제품(맥락별 추정기)의 실제 탑승 가능 연결편 **적중률 2/3 이상**
2. 잡을 수 있다고 했지만 실제로는 안전마진이 없었던 **위험한 오답 0건**
3. 네이버는 틀리고 제품만 맞은 **순증분 1건 이상** — 즉 지도가 부정확했던
   이벤트를 제품이 실제대로 교정한 사례

이면 1차 통과다. 표본 3건 미만이면 결과가 좋아도 `판정 보류`다.

⚠️ **도착시각 MAE는 통과 게이트가 아니라 진단값이다.** 신호를 보수적으로
과대예측하면(§7.4 RoadUpper fallback) 도착 MAE는 나빠지지만 **연결 안내는 정확할
수 있다.** 이전 판은 `MAE 30% 감소`를 게이트로 두어, 정확히 이 경우 — 신호 반영이
연결을 맞히는데도 — 를 탈락시켰다. MAE는 병목이 도보속도인지 신호예측인지를
진단하는 데만 쓴다. 위험오답 0이 안전 제약을 담당하므로, 보수적 과대예측(더
대기·놓침 쪽으로 안전한 방향)은 그대로 허용된다.

이 검증은 **해결책 성능**만 확인한다. 다른 사용자도 원하는지, 반복 사용하는지,
돈을 내는지는 별도의 사용자 수요 가설이다.

## 2. 비교 모델

| 모델 | 계산 | 역할 |
|---|---|---|
| `Naver` | 네이버 표시 도보시간 + 네이버 선택 연결 | 실제 경쟁 기준선 |
| `Speed` | 네이버 도보시간 × 개인 시간비율 | 속도 개인화의 순증분 |
| `Speed+Signal` | Speed + 첫 도보 실시간 위상 / 그 외 기대 신호대기 | 제품 예측 |
| `TMAP-Personal` | TMAP 시설별 거리 ÷ 개인 물리속도 | 실제 해결책의 순수 이동 모델 |
| `TMAP+Signal` | TMAP-Personal + 횡단보도별 기대 신호대기 | TMAP 기반 제품 예측 |
| `Kakao-Personal` | 카카오 도보거리 ÷ 개인 물리속도 | 장소명부터 자동화한 이동 모델 |
| `Kakao+Signal` | Kakao-Personal + 기대 신호대기 | 카카오 경로 기반 제품 예측 |

※ **'신호를 완벽히 알면 얼마나 정확해지나'(개선 천장)는 별도 모델로 두지 않는다.**
그 값은 트립에서 관측한 실제 신호대기(`actual.signal_wait_s`)를 `Speed` 도착에 더해
한 줄로 읽는다 — 예: E1 순수걷기 예측이 실제와 6.43초 차이이고 실제 신호가
118.93초이므로, 신호를 완벽히 알면 도착오차는 ≈6초까지 내려간다. 예전엔 이를
`Oracle`/`+RealSignal` 모델로 뒀으나, '실측'이 실시간 신호 API로 오해돼 없앴다
(애초에 통과 게이트엔 들어가지 않는 진단값이었다).

기본 개인 시간비율은 이전 무횡단 캘리브레이션의 `0.68`이다.
코드의 `speed_mps`는 `1.45배` 같은 비율이 아니라 실제 물리속도(m/s)이며,
신호의 통과 가능 창을 계산할 때만 사용한다.

신호 계산은 `docs/transit-routing-gtfs.md` §7의 규칙을 그대로 쓴다.

0. **세그먼트 병합 (신호 계산 전처리).** TMAP은 2단계 횡단(중앙분리대)을
   `facilityType=15` 세그먼트 여러 개로 쪼갠다. 그대로 두면 신호 대기가 실제
   신호 수보다 과다 계상된다(✅ Case 1: 실제 3신호인데 6세그먼트 → 630초). 그래서
   앞 세그먼트 끝과 다음 세그먼트 시작이 8m 안이면(중앙섬 폭) **하나의 신호로
   병합**한다(`tmap_client.merge_adjacent_crosswalks`). 별개 교차로는 사이에
   일반보행로가 있어 멀리 떨어지므로 안 합쳐진다. 아래 모든 규칙은 **병합된 신호
   단위**로 적용한다.
1. **첫 도보의 첫 횡단보도**이며 TMAP 횡단보도와 실시간 교차로가 50m 안에서
   매칭되고 예측 지평이 3분 이내면 실시간 상태·잔여시간을 고정 주기에 투영한다.
2. 같은 도보의 두 번째 횡단보도부터, 뒤쪽 도보, 실시간 미지원 지역,
   오래된 위상은 주기 기반 기대대기를 쓴다.
3. 어느 경우든 통과 조건은
   `녹색 잔여 ≥ 횡단거리 ÷ 사용자 속도`다.
4. 실시간 위상도 주기 기반 기대대기도 계산할 수 없지만 TMAP 횡단보도는
   검출됐다면(= 공공데이터에 cycle/green 이 없는 대부분의 경우), **두 추정기를 다
   계산해 소스별로 넣는다** — `score.py` 가 `…(상한)`·`…(유도)` 모델로 자동 출력한다:
   - **상한(RoadUpper)**: 거리별 보수 상한. 20m 이하 60초·초과 150초(7/23 calibration
     15m→3.54·16m→45.52·24m→120.77초로 학습, `signal_calibration.json` 고정). **항상
     과대(절벽 안전용).**
   - **유도(derived)**: `green = 7초 + 횡단거리÷1.0`(경찰청) · `cycle` = 도로등급 prior →
     `red²/(2·cycle)`. **평균(도착시각 정확), 배포 가능.** 표준데이터에 주기가 없어도
     `횡단거리`는 있으니 전국 적용된다(§7.4·signal-data-pipeline). ✅ Case 1: 유도가 상한을
     압도(Speed+Signal 상한 168.6 → 유도 14.0초).
   ⚠️ 유도는 평균이라 과소예측 위험 — **절벽 trip 에선 유도에 §6.6 안전마진을 얹거나 상한**을
   쓰고, 배차버스·도착시각 표시엔 유도를 쓴다.
5. 같은 신호 수에 OTP 기본값 15초와 기대값 20초를 적용한 결과도 민감도로 함께 출력한다.
6. TMAP 횡단보도도 얻지 못한 경우에만 `Signal unavailable`로 표시하고
   신호 모델 통과 판정에서 제외한다.

### 신호를 속도에서 격리해 검증한다 (§6.3 차별점)

⚠️ **빠른 사용자에겐 신호가 속도에 가려진다** — 빠른 속도는 도착을 당기고(차를 잡음) 신호는
늦추는데(차를 놓침), 둘이 상쇄되면 "내 속도+신호 ≈ 지도 보통속도+무신호"가 되어 답이 같아진다.
Case 1 이 신호 미검증인 이유가 이것(빠른 사용자 + 배차버스). **모델은 항상 내 속도+신호를 쓰되**,
신호 차별점을 **격리 검증**하려면:

- **`--ratio 1.0`**(보통 속도)로 돌려 속도 이득을 0으로 묶고, **절벽 trip**에서 신호만으로 연결이
  뒤집히는지 본다. 이건 진단 세팅이지 제품이 아니다(제품은 실제 속도).
- 신호 차별점은 **빠듯한 절벽 연결**에서 최대다 — 지도(보통속도·무신호)는 "탄다"는데 실제는
  "놓친다"가 되어 지도가 **위험하게 틀리는** 곳. 보통~느린 사용자일수록 크다.

기대대기(뒤쪽 도보·비실시간 분기, `docs/transit-routing-gtfs.md` §7.1·§7.4):

```text
E[wait] = red² / (2 × cycle)
```

첫 도보의 실시간 위상 투영에서만 통과 조건이 별도로 걸린다(§7.4). 이때는
횡단시간을 유효 녹색에서 뺀다.

```text
crossing_time = crossing_distance / user_speed
effective_green = green - crossing_time
통과 ⟺ 녹색 잔여 ≥ crossing_time
```

고정 주기, 균일 위상, `crossing_time ≤ green`이 전제다. 횡단 이동시간은
네이버 도보시간에 이미 포함되므로 기대대기에는 더하지 않는다. 이 기대값
공식과 API 부재 시 사용하는 TMAP 횡단거리별 보수 상한은 서로 다른 분기로
평가한다.

### 신호와 연결 판정의 분리 — 절벽(cliff) 규칙

`docs/transit-routing-gtfs.md` §6.3에 따라, 신호 대기가 **어느 차를 잡는지**를
바꾸는 것은 **시각표를 지키는 수단(지하철·기점 광역버스 등 절벽 O)** 에서만이다.
**배차간격 운영 버스(절벽 X)** 는 정류장 도착이 배차주기에 대해 사실상 무작위라
기대 대기가 도착시각과 무관하고, 버스 도착 불확실성(배차·뭉침)이 신호 90초를
삼킨다. 따라서 이벤트에 `cliff` 플래그를 둔다.

- `cliff: true` (기본): 신호 Δ가 도착시각(MAE)과 **연결 선택 게이트** 모두에 반영.
- `cliff: false` (배차버스): 신호 Δ는 도착시각(MAE)에만 반영하고, **연결 선택
  게이트에서는 제외**한다(순수 이동 도착으로 어느 차를 잡는지 판정). 신호
  과대·과소예측이 배차버스 연결을 잘못 뒤집는 것을 막는다.

즉 `cliff: false` 이벤트에서 신호 모델의 유효 축은 도착 MAE뿐이며, 그 MAE도
배차 대기 불확실성에 상당 부분 묻힌다. 신호 차별점의 진짜 검증은 절벽이 있는
`버스/도보 → 환승도보(신호) → 지하철` 조합에서만 성립한다.

## 3. 관측 단위

전체 트립이 아니라 **도보 뒤 하나의 연결편을 타는 사건**이 표본 하나다.

예를 들어 7월 23일 이동은:

```text
E1  출발지 도보 → 6211
E2  6211 하차 후 도보 → G8110
E3  G8110 하차 후 도보 → 55
```

세 이벤트로 나눈다. 중간에 다른 버스를 선택해도 각 이벤트의 입력·정답이
분리되므로 전체 경로 변경이 도보 모델 평가를 오염시키지 않는다.

## 4. 현장에서 남길 것

### 도보 시작 시점

1. 휴대전화 절대시각
2. 네이버 경로 캡처
   - 도보거리
   - 도보시간
   - 네이버가 선택한 연결
3. 목표 정류장의 버스 도착정보 캡처
   - 후보 차량 ID/노선
   - 각 차량의 `N분 후`
   - 캡처 절대시각

### 이동 중

1. 실제 도보 시작시각
2. 신호별 대기 랩
3. 뛰기·정지·경로 이탈 여부

### 정류장 도착 이후

1. 실제 정류장 도착시각
2. 후보 차량들의 실제 출발시각
3. 실제 탑승 차량
4. 자발적으로 앞차를 보냈는지

`실제로 탄 차`와 `물리적으로 잡을 수 있었던 가장 이른 차`는 다르다.
스코어러의 정답은 실제 정류장 도착시각과 후보 차량 출발시각으로 계산한
**가장 이른 안전한 연결**이다. 실제 탑승 차량은 별도로 기록한다.

### 4.1 절벽 trip 관측 프로토콜 (신호 차별점 검증용)

신호가 **어느 차를 타는지 뒤집는** 차별점(§6.3)은 절벽에서만 성립하므로, 그걸 검증하려면
**절벽 trip**을 관측한다: `버스/도보 → 환승도보(신호) → 지하철`. 지하철이라 놓치면 다음 열차
(헤드웨이만큼 점프)이고, 환승 도보에 신호가 있어야 한다.

> ⚠️ **관측만 하면 된다 — 신호 주기(cycle/green)는 측정하지 않는다.** product 예측은
> **유도**(횡단거리 기반, §7.4)가 만들고, truth 는 관측한 실제 신호 대기로 계산한다. "이
> 신호에서 몇 초 기다렸나"(스톱워치)만 기록하면 되지, "이 신호의 주기가 몇 초인가"(신호기
> 앞 폴링)는 잴 필요가 없다. **주기 측정은 예외 — 검증에서 유도가 그 절벽에서 위험오답을
> 낼 때만 그 횡단보도를 실측 승격**(1~2초 폴링 → `infer_timing`)한다.

이동 전:
1. 네이버 전체 경로 캡처 (환승 도보 시간·안내한 열차)
2. **환승 도보 직전** 절대시각 + **지하철 도착 시각표**(다음 2~3 열차) 캡처

이동 중 (환승 도보):
3. 환승 도보 시작 절대시각
4. **신호별 대기 랩** (스톱워치) — 몇 개 신호에서 각각 몇 초. `cliff=true` 의 핵심 입력
5. 뛰기·무단횡단 없이 평소 속도

승강장 도착 후:
6. 실제 승강장 도착시각 · 실제로 탄 열차 · 놓친 열차가 있으면 그 출발시각

인코딩: `cliff: true`, `bus_snapshot.candidates` = 열차 시각표, `actual.signal_wait_s` =
관측 신호 대기 합, `actual.connection_departures` = 열차 출발. `source: real`, `split: test`.
그러면 상한/유도 둘 다 자동 계산되고, 맥락별 제품(절벽=상한)이 위험오답 없이 지도를
이기는지 판정된다.

`tmap`은 선택 필드다. 좌표는 WGS84 경도(`lon`)·위도(`lat`)이며, 실제 도보
구간의 시작점과 목표 **정류장**을 넣는다. 좌표가 없는 과거 표본은 기존
`Speed+Signal`까지만 계산된다. TMAP 원본 응답은 파일로 저장하지 않고 평가
실행 중 메모리에서만 사용한다.

⚠️ **정류장 종점은 반드시 실측 정류장 좌표여야 한다.** TMAP·장소 검색이 종점을
건물/장소 좌표로 잡으면 도보 거리가 어긋나 연결 안내가 뒤집힌다(✅ Case 1 E1:
건물 939m vs 실제 정류장 781m). 정류장 좌표를 직접 모르면 화면의 **정류장
번호(ARS)**를 주면 모델이 TAGO `getSttnNoList`로 실측 좌표를 역조회한다
(`stop_client`). 지점은 다음 두 형태를 쓴다:

```json
"end": {"lon": 127.1145, "lat": 37.3919667, "name": "백현마을1단지"}
"end": {"stop": {"city_code": 31020, "ars": "07488", "name": "백현마을1단지"}}
```

둘 다 있으면 `lon/lat`를 우선한다(오프라인 재현 유지 + ARS는 출처 기록). ARS
앞자리 0은 자동으로 뗀다(07488→7488). 이 역조회는 data.go.kr 정류소정보
(15098534) 승인 키(`STOP_API_KEY`/`GBIS_BUS_KEY`/`DATA_GO_KR_KEY`)를 쓴다.

`kakao`를 사용하면 장소명으로 좌표를 찾고 카카오 도보 경로의 전체 좌표열을
가져온다. 동명 장소가 있으면 `near`로 검색 중심과 반경을 제한하거나
`result_index`로 후보를 고정한다. `end`에 목표 정류장을 직접 넣을 수도 있고,
`trip_end`와 `prefer_vehicle`을 넣으면 카카오 대중교통 후보 중 해당 노선이
포함된 경로의 최초 승차점 좌표를 자동 추출한다. 관측 검증에서는
`prefer_boarding_stop`도 함께 넣어 실제로 걸어간 정류장이 아닌 후보가
선택되는 것을 막는다. 후보에 없으면 자동 추정을 강행하지 않고 오류로 중단한다.
아파트 출입구처럼 장소 대표점과 실제 시작점이 다른 경우에는 `start`에
휴대전화가 기록한 `lon`·`lat`를 직접 넣는다. `--hybrid`에서는 동일한
시작·종료 좌표를 TMAP에 넘겨 `facilityType=15` 횡단보도 구간을 검출한다.
TMAP은 신호 주기·녹색 시간·현재 위상을 제공하지 않으므로 그 값은
`crosswalks.json` 또는 실제 관측으로 계속 보완한다.

### `source`와 `split`

| 값 | 의미 | 통과 판정 포함 |
|---|---|---|
| `source: demo` | 인위적으로 만든 예시 | 제외 |
| `split: calibration` | 이미 결과를 보고 모델을 만든 과거 자료 | 제외 |
| `source: real`, `split: test` | 모델을 고정한 뒤 얻은 새 관측 | 포함 |

7월 23일 E1은 입력 파이프라인 확인을 위한 `calibration` 표본으로 이미 들어 있다.
새 실험에서는 모델 비율·신호식을 바꾸지 않고 `test`만 추가한다.

## 6. 횡단보도 데이터

`crosswalks.json`:

```json
{
  "cw_home_1": {
    "source": "real",
    "dist_m": 18,
    "cycle_s": 95,
    "green_s": 20,
    "stdg_cd": "11140",
    "crsrd_id": "교차로ID",
    "direction": "et"
  }
}
```

- `dist_m`: 연석부터 반대 연석까지의 횡단거리
- `cycle_s`: 녹색 시작부터 다음 녹색 시작까지
- `green_s`: 진입 가능한 보행 녹색시간
- `stdg_cd`·`crsrd_id`: 실시간 API 교차로 식별자
- `direction`: `nt/ne/et/se/st/sw/wt/nw`. TMAP 선형으로 자동 추정하지만
  실제 API 방향과 다르면 이 값으로 고정한다.
- 가능하면 3주기 평균
- 감응식이면 메모하고 별도 표본으로 표시

실시간 API는 현재 상태와 잔여시간만 주며 `cycle_s`와 `green_s` 필드는 없다.
주기는 전국횡단보도표준데이터의 제공값을 우선 쓰고, 없으면 같은
`crsrd_id + direction`을 1~2초 간격으로 폴링해 녹색 시작 간격을 2회 이상
관측한다. `signal_client.infer_timing()`은 그 전이 기록을 주기와 녹색시간으로
변환한다. 성남·판교처럼 실시간 API가 없는 지역도 주기만 확보하면 기대대기
분기로 평가할 수 있다.

횡단거리 이동시간 자체는 네이버 도보시간에 이미 포함된 것으로 본다.
신호 모델은 **추가 대기시간만** 더한다.

주기 데이터가 아직 없으면 `crossings: []`로 Speed 모델부터 검증한다.
관측한 실제 신호대기(`actual.signal_wait_s`)는 통과 판정엔 안 쓰지만, 개선 천장
진단(신호를 완벽히 알았을 때의 도착오차)에 필요하므로 계속 기록한다.

## 7. 실행

### 환경파일

환경파일은 공통과 구성요소 전용으로 나눈다.

| 파일 | 역할 |
|---|---|
| `find-path/.env` | 여러 구성요소가 같이 쓰는 공통 키 |
| `spike/validation/.env` | 기술 Validator 전용 키 |
| `collector/.env` | 수집기 전용 키 |

Validator의 우선순위는 `운영체제 환경변수 → spike/validation/.env →
find-path/.env`다. 처음 한 번 필요한 파일을 만든다.

```bash
cp .env.example .env
chmod 600 .env
cp spike/validation/.env.example spike/validation/.env
chmod 600 spike/validation/.env
```

필요한 기능의 키만 채운다.

```dotenv
TMAP_APP_KEY=
KAKAO_REST_API_KEY=
SIGNAL_API_KEY=
```

경량 Validator는 API를 쓰지 않으므로 두 환경파일이 없어도 실행할 수 있다.

```bash
cd spike/validation

# 캘리브레이션 포함 전체 확인
python3 score.py

# 새 테스트 표본만
python3 score.py --split test

# spike/validation/.env 또는 find-path/.env의 TMAP_APP_KEY로 조회
python3 score.py --tmap
python3 score.py --tmap --split test

# 장소명→좌표→카카오 도보 경로
python3 score.py --kakao

# 카카오 자동 좌표/경로 + TMAP 시설 유형
python3 score.py --hybrid

# TMAP 횡단보도 + 실시간 보행신호. 실시간 불가 시 주기 기반 기대값
python3 score.py --hybrid --signals

# 안전마진 민감도
python3 score.py --buffer 30
python3 score.py --buffer 60
python3 score.py --buffer 90

# 개인 시간비율 민감도(판정 확정용이 아닌 진단)
python3 score.py --ratio 0.65
python3 score.py --ratio 0.72

# 실측 횡단보도의 속도별 유효 녹색 변화
python3 score.py --sweep

# 단위 테스트
python3 -m unittest test_score.py
```

### 전체 여정 연결 실행

연결 이벤트별 `score.py`와 별도로 `journey_score.py`는 다음 네 층을 실제
순서대로 연결한다.

```text
TMAP 대중교통 itinerary
→ 모든 WALK leg를 TMAP 보행자 API로 재조회
→ 개인 물리속도 적용
→ WALK leg마다 보행신호 적용
→ BUS/SUBWAY sectionTime 및 승차 대기시간 연결
→ 전체 도착시각
```

입력 예시는 `journey_case.example.json`이다.

```bash
# TMAP 후보와 물리 경로 확인
python3 journey_score.py journey_case.example.json --list-routes

# 요청한 노선 순서가 후보에 있을 때 전체 계산
python3 journey_score.py journey_case.example.json

# 특정 TMAP 후보를 진단
python3 journey_score.py journey_case.example.json --itinerary-index 0
```

TMAP 대중교통 응답은 대중교통 `sectionTime`은 주지만 승차 대기시간은 주지
않는다. 따라서 `transit_waits_s`에 각 대중교통 leg의 사전 ETA/자체 시각표
기반 대기를 넣지 않으면 계산기는 `complete=false`와
`missing_wait_legs`를 반환한다. 누락 대기를 0초로 간주한 총시간은
하한 진단값일 뿐 제품 예측이나 정확도 판정에 쓰지 않는다.

`prefer_routes`가 TMAP 후보에 없으면 다른 경로를 억지로 비교하지 않고
중단한다. 물리 경로가 다른 전체 여정의 실제 도착시간을 비교하면 도보·신호
모델과 경로 선택 차이가 섞이기 때문이다.

기본 안전마진은 60초다. 실제 버스가 최초 화면보다 30~90초 당겨지는 관측을
반영한 값이며, 30/60/90초 결과를 함께 보고 민감도를 확인한다.

## 8. 결과 읽기

각 이벤트에서 출력하는 값:

- 모델별 정류장 도착 예상시각
- 실제 대비 도착 오차
- 모델이 선택한 가장 이른 연결
- 실제로 잡을 수 있었던 가장 이른 연결
- 연결 적중 여부
- 위험한 오답 여부

요약:

- MAE: 정류장 도착시각 평균 절대오차
- 중앙 AE: 소표본에서 극단값 영향을 줄인 오차
- 연결정확도
- 위험오답 수
- 순증분: 네이버는 틀리고 제품만 맞은 표본

신호 병목은 별도 모델 없이 진단한다: `Speed`(신호 미포함)의 도착오차와 관측된
실제 신호대기(`actual.signal_wait_s`)를 비교한다. `Speed` 도착오차가 실제 신호
크기만큼 벌어지고, 순수걷기 오차 자체는 작으면 — 병목이 도보 속도가 아니라 신호
예측이라는 뜻이고, 신호 데이터(횡단보도 주기) 확보의 가치가 크다.

## 9. 제외 규칙

다음은 `valid: false`로 남기고 통과 판정에서는 제외한다.

- 달림 또는 무단횡단
- 개인 용무로 정지
- 경로 이탈
- 버스 도착 캡처의 절대시각을 모름
- 후보 차량의 실제 출발을 확인할 수 없음
- 무배차로 계획 자체가 붕괴

경로 변경 자체는 제외 사유가 아니다. 연결 이벤트를 나누고 변경 이유와 실제 후보
차량 출발을 기록하면 별도의 유효 표본으로 사용할 수 있다.
